## 1. Общая оценка архитектуры

Модульный монолит (Spring Boot 3.4 / Java 21 / PostgreSQL 16 + PostGIS) + 2 Flutter-приложения + React-админка. Решение оправдано: нагрузка, измеренная на одной машине, укладывается с большим запасом, а микросервисы, Redis и Kafka не нужны.
Сильные стороны: инварианты в БД (частичные уникальные индексы на «одна активная поездка», «один активный оффер», неизменяемый леджер на триггерах, `CHECK` на неотрицательный кошелёк клиента); сервер — единственный источник денег (клиент не передаёт цену); интерфейсы `RouteProvider` / `PaymentProvider` / `SmsSender` отделяют заглушки от боевых интеграций.
Слабые стороны: realtime-события живут в памяти одного инстанса (нельзя масштабировать на несколько реплик без доработки); лимитер запросов и блокировка логина — тоже per-instance; `ride_locations` растёт без политики хранения; JDBC вместо JPA (осознанное отклонение от ТЗ).

## 3. Результаты функциональных проверок

Автоматизировано и пройдено локально: backend **54/54**, admin **7/7**, `jolay_core` **9/9**, customer **8/8**, driver **4/4**; `flutter analyze` — без замечаний во всех трёх пакетах; `npm audit` — 0 уязвимостей; сборка admin — успешна.
Сценарий «клиент → заказ → диспетчер → водитель → поездка → оплата → рейтинг → история → админка» выполнен автотестом для наличных, кошелька и карты (песочница), а также отмены клиентом/водителем, истечения, отсутствия водителей, возвратов, неуспешной оплаты, дубликатов вебхука.
**Не выполнено:** живой прогон приложений на устройстве против реального backend; сценарии доставки и партнёра (не реализованы); тест потери сети и переподключения WebSocket на клиенте.

## 4. Финансовая целостность

Проверено тестами: фиксированная цена на сервере; комиссия по категории; кошелёк — только через леджер; каждая проводка сбалансирована (сумма 0); кеш-баланс = сумма записей; леджер нельзя изменить/удалить (триггеры); баланс клиента не уходит в минус (CHECK); повтор вебхука / повтор event-id / подмена суммы / неверная подпись не создают проводок; повторный и двойной возврат отклоняются; возврат потраченного пополнения отклоняется; идемпотентные ключи для поездки, пополнения, оплаты, проводок.
Добавлено в аудите: `GET /admin/finance/reconciliation` (суммы, несбалансированные проводки, расхождение кеша, успешные платежи без проводки, оплаченные поездки без проводки, зависшие платежи); тест проверяет и «OK» и «CRITICAL» при подделке.
Открыто: нет плановой сверки с реестром шлюза; **выплаты водителям не реализованы**; комиссия отмены для не-кошельковых способов только записывается; кошелёк водителя может уходить в минус до порога (после порога водитель не получает заказы — проверено тестом диспетчера косвенно).
Юнит-экономика: расчёт прибыли **невозможен** без данных о расходах (эквайринг, SMS, карты, хостинг, поддержка, бонусы). Для справки по текущим тарифам Economy: поездка 7 км / 15 мин = 1 340 ₸, комиссия 15 % = 201 ₸ выручки платформы (`PricingServiceTest`). Это иллюстрация арифметики, а не оценка рентабельности.

## 6. База данных и PostGIS

Конфигурация: `geography(Point,4326)` для точек, `geography(Polygon,4326)` для зон (отличие от совета использовать `geometry` для полигонов: для одной зоны Алматы без разницы; при сложных многоугольниках в нескольких городах стоит перейти на `geometry` + проекцию), GiST-индексы на `driver_locations`, `service_zones`, `places`; одна строка последней позиции на водителя, история пути отдельно (`ride_locations`).
Измерено `EXPLAIN (ANALYZE)` на 100 000 водителей / 70 165 позиций онлайн-водителей:

| Запрос | До | После | Комментарий |
|---|---|---|---|
| Подбор кандидатов, радиус 2 / 6 км, плотный сценарий (≈480 водителей в 2 км) | 31 / 118 мс | ~10–11 мс | KNN `<->` по GiST с пулом 30 (`dispatch.candidate_pool`) |
| То же в ещё более плотной выдаче (≈1 470 в 2 км) | 24 / 70 мс | 21 / 55 мс | выигрыш 10–25 %; плотность заведомо выше реальной |
| ETA ближайшего водителя (вызывается 4× на оценку цены) | 76–89 мс (seq scan по `vehicles`) | 19 мс | CTE с KNN на 100 позиций, затем фильтры |
| Любой запрос при `jit=on` | один запрос 19 мс превратился в **2,7 с** | — | **Исправлено**: `SET jit = off` для пула соединений |
| 40 000 upsert позиций | 0,85 с, **20,5 МБ WAL** | 0,78 с, **~1 КБ WAL** | `driver_locations` стала UNLOGGED + fillfactor 70 + агрессивный автовакуум (миграция V4) |
Оговорки: плотность 58 онлайн-водителей/км² в тесте почти наверняка выше реальной; план `rides` по клиенту/статусу не измерялся на больших объёмах (в тесте таблица пустая); при падении БД UNLOGGED-таблица пуста до следующего GPS-пакета водителей (диспетчер и так игнорирует позиции старше 60 с); таблица не реплицируется на standby.
Транзакции и конкуренция: проверено — 6 параллельных диспетчеров на одного водителя дают один оффер; 4 параллельных «принять» одного оффера — один победитель; под нагрузкой 150 параллельных заказов 0 водителей с двумя офферами и 0 с двумя активными поездками.
Миграции: 4 (V1 схема, V2 справочники, V3 пул кандидатов, V4 тюнинг), применены с нуля в GitHub CI на чистом PostGIS-контейнере и локально; изменения только новыми миграциями.
Открыто: политика хранения/партиционирования `ride_locations` (≈1 строка/4 с на активную поездку — десятки миллионов строк в месяц при росте); индексы для отчётов; пулы соединений не тюнились.

Разброс между прогонами до ±40 % (общая машина, холодный JVM) — цифры нельзя экстраполировать на боевую ёмкость. Не измерялись: платежи/вебхуки под нагрузкой, WebSocket-рассылка, длительный (soak) тест, отказы (рестарт backend посреди поездки, потеря БД).
Проверено в аудите: backend-образ собирается (CI); prod-профиль реально запущен — отказ при небезопасной конфигурации, readiness/liveness на порту 8081, метрики только там, JSON-логи (ECS) без ошибок уровня ERROR, `X-Request-Id` возвращается; исправлены пробы Docker/Kubernetes (раньше смотрели на неверный порт в prod).
**Бэкап/восстановление проведены:** `pg_dump -Fc` 100 000 водителей — 13 МБ за 1,4 с; восстановление в чистую БД — 2,6 с; идентичны число водителей/позиций, версия миграций (4), UNLOGGED-признак, сумма леджера 0.00.
